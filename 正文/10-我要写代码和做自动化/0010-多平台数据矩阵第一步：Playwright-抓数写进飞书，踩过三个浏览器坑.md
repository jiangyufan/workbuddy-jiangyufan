# 多平台数据矩阵第一步：Playwright 抓数写进飞书，踩过三个浏览器坑
## 我想知道自己的每篇文章，每天在各平台的数据
我是一个程序员，也是内容创作者，写过几百篇文章，接触过不少创作平台。

**这次的需求很具体：**用 Playwright 爬取多平台的文章数据，写进飞书表格，然后做成自动化任务。说得高大上一点，叫「搭建多平台数据矩阵」。

**做成之后的好处很直接：**我想统计每个平台下每篇文章每天的数据，跑一次自动化任务就行，不用一个个后台去点。

这篇文章记录的是第一步——把 CSDN 这一个平台的数据打通。不同平台的字段不一样、后台展示方式也不一样，所以多平台一定会遇到不同的坑，先把一个打穿，比同时铺五个靠谱。

## 技术选型定下来，第一件事是调用 lark-sheets
和 WorkBuddy 确认技术选型是 Python + Playwright 之后，它开始搭项目框架和环境。

它做的第一件事不是写爬虫，而是加载一个叫 lark-sheets 的 Skill——飞书官方的能力套件，专门操作飞书电子表格。

为什么先做这件事？因为整条链路里有一半是「写表格」。创建子表、读写单元格、设置格式，全都通过这个 Skill 完成。爬虫只是取数，落地全靠它。

**这里有个顺序上的经验：**先验证「能写进去」，再验证「能抓出来」。因为写表格涉及 API 授权、空间 ID、子表结构，变量比抓取多，先把它打通，后面数据出问题就能确定是爬虫的问题。

前提是你已经给它配好飞书的 MCP，在 WorkBuddy 里叫 Connector 连接器。没配过的话，这一步会直接卡住。

## Playwright 为什么自带一个 Chromium
另一个值得说清的技术点：Playwright 不直接用你电脑上的 Chrome，而是自带一个版本锁定的 Chromium。

原因是不信任电脑上随时会更新版本的 Chrome——万一 Chrome 自动升级，Playwright 的控制协议可能就不兼容了。自带一个验证过的版本，能确保每次运行行为一致。

Chromium 可以理解成 Chrome 的「开源裸版」，技术内核一样，外观功能几乎相同，只是少了谷歌那些额外服务集成。

这不是细节洁癖，是稳定性的基础。你写脚本是为了每天自动跑，一次不兼容就全断。

## 两种保留登录态的方案，WorkBuddy 给了分析
真正的难题不是抓数据，是抓需要登录的后台数据。CSDN 创作者后台要登录，脚本怎么带着登录态跑？

它给了两种方案。第一种：先关掉所有 Chrome 窗口，再启动 Chrome 并加一个调试端口参数，最后让脚本通过 CDP 协议连到这个已启动的 Chrome 上，这样所有登录态都保留。

**第二种：**直接关掉 Chrome，脚本用你自己的 Chrome Profile 启动浏览器，抓完再自动关闭。

两种方案都是先把数据存到本地 JSON，再写入飞书子表。这个中间层设计值得学——抓取和写入解耦，出了问题能分开排查，也能重跑写入而不用重抓。

作者当时不懂两者区别，看到 WorkBuddy 推荐第一种就照做了。结果第一种踩了三个坑，最后还是转到了第二种。

## 坑一：Chrome 单实例机制，让调试端口失效
**第一种方案听起来很美：**只要在快捷方式上永久加上调试端口参数，之后正常用 Chrome，脚本随时能连上去，不干扰日常使用，一劳永逸。

于是把快捷方式全改了，然后按要求完全关闭 Chrome 再重新打开。结果它提示「调试端口还没激活」。

原因是 Chrome 有一个「单实例」机制：如果 Chrome 已经在运行，哪怕只是后台进程，你从快捷方式点击打开，它不会启动新进程，而是给已有进程发消息让它开个新窗口。

这意味着已有进程的启动参数——那个没有调试端口的参数——决定了所有新窗口的行为。你改快捷方式没用，因为根本没启动新进程。

## 坑二：新版本安全策略要求指定数据目录
彻底杀掉 Chrome 进程后，下一秒就报错了：DevTools remote debugging requires a non-default data directory. Specify this using --user-data-dir。

这是 Chrome 新版本的安全策略：开启远程调试时必须显式指定用户数据目录，不能用默认目录。这也是调试端口一直不生效的另一半原因。

修复很简单，加上 --user-data-dir 参数，指向一个指定的目录。

这两个坑连起来看很有意思：一个是进程机制，一个是安全策略，都不是 Playwright 的问题，是 Chrome 自己的规则。这类坑只能踩过才知道。

## 坑三：复制 Profile 之后，登录态还是失效
调试端口生效后，新的问题来了：这个 Chrome 用的是空白 profile，没有任何登录状态。

于是它把我的 Chrome 登录数据复制了过来，包括 Cookies，打算用这个带登录数据的 debug profile 启动 Chrome，用 Playwright 连上去测抓取。

结果打开的页面根本没有登录。原因是 Chrome 用 DPAPI 加密方式保存登录凭证，复制到新 profile 目录之后解密失败。

**结论很明确：**复制 profile 这个方案只能保留部分 Cookie，不能完全保留登录态。参数指定了非默认目录，意味着是一个全新的空白 profile。

这正是第一种方案走不通的根本原因。技术方案看着能省事，但撞上了浏览器加密机制这条硬墙。

## 转到第二种方案，又踩了一个「登录窗口期」
第一种没起色，作者问能不能切到第二种，WorkBuddy 直接建议赶快转。

第二种是脚本用 launch_persistent_context 启动 Chrome，直接用真实 Profile 目录。代价是运行时要先关闭 Chrome，跑完再打开。

脚本跑起来弹出一个登录窗口，但作者当时正好有事，错过了窗口期——后来才知道一开始的登录窗口期只有 4 分钟。

于是让它把窗口期改成 10 分钟。这一步很实用：登录窗口期是这种方案的必需参数，太短会导致你还没登录完脚本就超时退出。

改完之后脚本一次跑成功了，数据直接写进飞书表格。

## 第一次成功但有瑕疵：展现量全空
成功的第一次并不完美。表格里除了「展现量」一栏是空的，其他字段都正常。

原因是 CSDN 创作者后台的「内容管理」界面里，看不到展现量。这个字段藏在别的地方。

作者随即告诉它两个可以拿到展现量的位置：一是在「管理 - 内容管理」里点每篇文章右侧「操作」中的「数据」选项，能看到当前展现量；二是在「数据 - 作品数据」里选「单篇文章分析」，也能看到每篇文章的展现量。

然后让它自己选一种方式实现。它选了第二种，理由很有意思：一张表就能看到所有文章的展现量，不需要每篇文章点一次。

**这个选择说明了一件事：**当你把「有哪些可选路径」告诉它，它会按效率挑，而不是照你第一句话机械执行。这就是给足上下文的价值。

## 拆解这个任务：四个可复用的做法
把这个案例拆开，有四件事可以搬到别的项目里。

一，配置文件集中管理。第一步就建了 config.py，把平台入口网址、飞书表格 ID、字段定义（日期、展现量、阅读量、点赞、收藏、评论）全写在一处。其他脚本启动时直接 import config 当字典用，不用每个脚本硬记去哪个网址、写到哪个表。

二，抓取与写入解耦。数据先落本地 JSON，再写飞书，某一步失败可以单独重跑。

三，先打通一个平台再铺开。多平台字段不同、后台不同，坑一定不同。一个打通了，后面的平台就有了模板和排查经验。

四，遇到浏览器层的坑，优先换方案而不是硬修。第一种方案的三个坑都撞在 Chrome 的机制上，继续修下去成本高于换方案。

## 最后的效果：一张表看所有文章每天的数据
最终的效果是一张飞书子表：每行是一天的日期，六列分别是展现量、阅读量、点赞、收藏、评论，数字会随时间累积。

配上自动化定时任务，每天自动拉取一次，这张表就成了一份持续生长的内容资产台账——你能看到某篇文章是第几天开始起量、哪个平台的转化更好。

这件事的真正价值不在爬虫技术，在于「数据从平台后台搬到你自己手里」。平台后台只会给你看几天的数据，搬出来之后你想怎么分析都行。

下一步才是铺多平台。有这一个平台打底，加上配置文件的结构，后面每加一个平台就是复制一份配置、改几处网址和字段。

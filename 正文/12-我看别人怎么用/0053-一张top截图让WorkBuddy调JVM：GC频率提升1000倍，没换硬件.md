# 一张top截图让WorkBuddy调JVM：GC频率提升1000倍，没换硬件
## 服务器快撑不住了
一台 AWS EC2 服务器出了状况：Spring Boot 应用跑了段时间后，内存占用越来越高，top 一看，Java 进程直接吃了 60.4% 的物理内存——一台 8GB 的机器，光这个进程就干掉了将近 5GB。

起因是服务器内存快爆了。更麻烦的是，JVM 参数是我当初随手配的：8GB 内存配了一半，就写了 -Xms4096m -Xmx4096m，加个 OOM 堆转储，什么 GC 收集器、元空间限制、GC 日志……说白了就是——能跑，但跑得不太健康。

我自己调过 JVM，知道这活有多烦：要分析 GC 日志、看对象分布、试参数、重启观察、再调整，一套下来大半天就进去了。然后我想起手头有个 WorkBuddy，要不让它试试？

## 第一步：一张截图 + 一句话
我就干了一件事——把 top 命令的截图发给 WorkBuddy，附上一句："在这台服务器上，我的 JVM 能不能再优化一下？Spring Boot 单体应用。"

它识别出截图里的所有数据（JVM 版本 OpenJDK 17、CPU 2 核、内存 7.6GB、堆大小 4GB），直接列出三个问题：非堆内存膨胀严重；没指定 GC 收集器；缺关键生产参数（没有 GC 日志、没有元空间限制、没有停顿目标）。

最关键的是，它还给了一个立即可用的优化版启动参数——零风险，堆大小不变，只是补齐了该有的调优参数。

*WorkBuddy 一眼看出 GC 频率提升 1000 倍的优化空间*

## 第二步：把GC日志也发过去
我以为到这就结束了。结果它说："把 GC 日志发给我看看，我能给你更精准的建议。"我按建议先加上 GC 日志参数重启跑了一会儿，再把 gc.log 传上去。

分析完发现一个致命问题：这机器只有 2 核 CPU。2 核 + 4GB 堆是灾难配方——4GB 堆分给 2 个 CPU 核，每核要负责 2GB 的 GC 压力。日志里的证据很明确：最大 Young GC 停顿达到 255ms（目标才 200ms），Eden 区一会儿 160MB、一会儿暴涨到 2432MB 就触发一次 GC。

## 结果：GC频率提升1000倍，停顿下降94%
它给了两个方案，我选了激进方案 B——把堆缩到 3GB。调整后 GC 频率提升了 1000 倍，GC 停顿下降 94%，关键是不用升级硬件，在 2 核 CPU 上完美稳定运行。运维同事问我："你太强了，你换机器了？"

中间也踩过坑：直接抄它给的参数时遇到过 "VM option ... is experimental" 的报错，需要按提示加上解锁实验参数的开关——AI 给的方案要能跑通，还得自己动手验证一遍。

## 一句实话
以前调 JVM 要大半天，现在一张截图 + 一份日志，它把分析、方案、参数都给出来了。但"选哪个方案、要不要升级硬件、参数能不能跑通"，这些判断仍然在人手里。工具把脏活干了，决策权别交出去。
